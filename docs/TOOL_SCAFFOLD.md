# ツール標準セット

Blender 側（`D:\BlenderData\addons\dev`）で「あってよかった」ものを Maya 向けに
置き換え、最初から全ツールに用意するための決めごと。 毎回ゼロから相談し直さなくて
済むように、**何を・なぜ・どう作るか**をここに固定する。

新規作成は `/new-tool <名前>`、既存ツールへの後付けは `/scaffold <名前>`。
充足状況の確認は `python tools\check_tools.py --list-missing`。

---

## この環境の前提 — 実機が手元に無い

Blender 側との決定的な違いはこれ 1 点で、標準セットの設計はほぼすべてここから
導かれている。

| | Blender 側 | ここ（Maya） |
|---|---|---|
| 実機 | 開発機に入っている | **会社にしかない** |
| 反映 | リポジトリを直読み → Reload Addon | **push → 実機で更新ボタン** |
| 「動いた」の確認 | その場でできる | **次に出社するまでできない** |

そこから来る帰結:

1. **手元で実行できる範囲を最大化する** → `core.py`（Maya 非依存）への分離
2. **実機でしか出ない事故を機械で潰す** → `_REMOTE_FILES` 検査・バージョン同期検査
3. **更新が届いたかをユーザーが確かめられるようにする** → UI のバージョン表示
4. **「テストが通った」を「動いた」と書かない** → 報告と PROGRESS.md の書き方

---

## 開発サイクル

```
自宅                                   会社
────────────────────────────────       ──────────────────────────
1. コードを書く
2. tests を走らせる（Maya 不要）
3. check_tools.py で 0 error
4. commit して push        ────────►   5. ツール UI の「GitHub から更新」
                                       6. 実機で動作確認
                                  ◄──── 7. 結果を PROGRESS.md に反映
```

**4 を飛ばすと 5 は何も起きない。** `install.py` は GitHub の commit SHA を見に
行くので、ローカルのコミットは実機から見えない。 `/wrapup` が push まで含んでいる
のはこのため。

初回だけは `install.py` をブラウザで保存して Maya にドラッグ&ドロップする。
**2 回目以降のドラッグは効かない**（Maya は同じファイルパスの
`onMayaDroppedPythonFile` をセッション内で 1 度しか呼ばない）ので、更新は
UI のボタンかシェルフの右クリックから行う。

---

## 配布はリポジトリ直下のハブ 1 本

**`install.py` はリポジトリ直下に 1 本だけ。** ツールごとには持たない。

```
maya-scripts-dev/
├── install.py            ← 全ツール共通のハブ。 配るのはこの Raw URL 1 本
├── <tool_a>/
│   └── <tool_a>/         ← ハブはこの「同名 2 段」の形を探す
│       └── __init__.py
└── <tool_b>/
    └── <tool_b>/
        └── __init__.py
```

ハブは GitHub の tree API を 1 回叩いてリポジトリ全体のパス一覧を取り、
`<名前>/<名前>/` の形になっているフォルダを**ツールと見なして中身を全部配る**。
だから新しいツールを足しても、**どこにも登録しなくていい**。

### なぜツールごとに持たないのか

| | ツールごと（旧） | ハブ 1 本（現行） |
|---|---|---|
| API コール | ツール数 × 1 | **常に 2**（SHA 解決 + tree） |
| 配布リスト | `_REMOTE_FILES` を手で同期 | **宣言そのものが無い** |
| 新ツールの登録 | install.py を書く | 不要（形が合っていれば拾われる） |
| エンドユーザー | ツールごとにドラッグ | **1 回のドラッグで全部** |

**API コールが効く理由**: 未認証の GitHub API は **1 時間 60 回 / IP**。
会社では NAT で全員が同じ枠を共有するので、ツールが増えるほど「更新しようと
したら 403」が現実味を帯びる。 ハブなら本数に関係なく 2 回で済む。

**`_REMOTE_FILES` が消せる理由**: tree walk は §1-10 の教訓が挙げていた
代替案そのもの。 ツールごとに走らせるなら本数分の API コールが要るので割に
合わなかったが、ハブなら 1 回で全部見える。 宣言が無ければ、宣言と実体が
ずれる事故（自宅では絶対に再現しない）も起きない。

### 単一障害点にならないのか

ならない。 シェルフの Update スニペットも `dev_tools.py` の更新ボタンも、
**毎回 GitHub からハブを取り直して `exec` する**。 ローカルのハブが壊れていても
関係なく、ハブ自体に不具合があれば push すれば次の更新で直る（これは旧方式と
同じ性質）。

**ハブがどのパッケージにも依存しない**ことだけは守る。 パッケージが壊れていて
import できないときに、直すための更新まで走らなくなると詰むため。

---

## なぜパッケージ構成なのか

ツール 1 本 = フォルダ 1 つで、中に**同名のパッケージ**を持つ。 この
「同名 2 段」がハブの探索条件そのもので、崩すと**丸ごと配布されない**
（`tests/test_installer.py` と `check_tools.py` が両方から検査する）。

単一ファイル構成にしない理由は、後から分割するときに配置の形が変わって
しまうため。 最初からパッケージなら、ファイルを足すだけで済む
（ハブが中身を全部拾うので、足したことを宣言する必要すら無い）。

---

## なぜ `core.py` と `ui.py` を分けるのか

**開発機に Maya が無いので、`cmds` を呼ぶコードは実機に持っていくまで一度も
実行されない。** 一方 `maya` を import しないコードは、手元の Python でそのまま
動き、テストで境界条件まで詰められる。

つまり **`core.py` に寄せた分だけ、自宅で検証できる範囲が広がる**。 これは好みの
問題ではなく、この環境で品質を上げる唯一の実効的な手段になっている。

| 層 | 中身 | 自宅で検証できるか |
|---|---|---|
| `core.py` | 名前の生成・パース・検証、計算、データ変換、判断 | **できる（本物の Python として動く）** |
| `ui.py` | `cmds` による UI 構築、値の受け渡し | 呼ばれたことだけ（スタブ） |
| `dev_tools.py` | バージョン表示・更新（共通・触らない） | 同上 |

`ui.py` の理想形は「`cmds` で値を集める → `core` に渡す → 返ってきた結果を `cmds` に
流す」だけ。 `ui.py` に `if` が増えてきたら、それは `core` に移すべきロジック。

`tools/check_tools.py` は `core.py` が `maya` を import していたら警告する。

## 標準セット

| 資産 | 中身 | 無いとどうなるか |
|---|---|---|
| `<pkg>/__init__.py` | `__version__` / `SHELF_LABEL` / `show()` | 版数の情報源が無く、起動の入口も無い。 **そもそもハブに拾われない** |
| `<pkg>/core.py` | Maya 非依存の純ロジック | 自宅で検証できる範囲がゼロになる |
| `<pkg>/ui.py` | `cmds` による UI | — |
| `<pkg>/dev_tools.py` | バージョン表示と「GitHub から更新」 | 実機で更新できない（毎回ドラッグし直し） |
| `SPEC.md` | 現行仕様・アーキテクチャ・設計判断 + `## 実装状況` | 何を作ったのか半年後に分からない |
| `README.md` | ユーザー目線の機能・使い方・**インストールと更新の手順** | ユーザーが更新方法を知らずに詰まる |
| `CHANGELOG.md` | 版ごとの経緯・試行錯誤 | SPEC が経緯で膨らむ |
| `tests/` | Maya 非依存の回帰テスト | push 前の足切りが無くなる |

## バージョンの扱い

**`<pkg>/__init__.py` の `__version__` が唯一の情報源。** 同期先は 3 箇所:

1. `SPEC.md` の「概要」
2. ツールの `README.md` の「概要」
3. ルート `README.md` の一覧表

**コードを変えたら必ず上げる。** Blender 側にも同じルールがあるが、ここではより
切実な理由がある — 実機が手元に無いので、**更新が届いたかどうかを確かめる手段が
「UI に出ているバージョン番号」しかない**。 据え置くと、ユーザーも自分も
「更新されたのか、届いていないのか」を区別できなくなる。

だから **UI のバージョン表示は消さない**（`dev_tools.build_footer()`）。
`tests/test_tool_meta.py` がその表示の存在まで検査している。

## 配布漏れをどう止めるか（旧 `_REMOTE_FILES` 問題）

かつては `install.py` がダウンロード対象を `_REMOTE_FILES` のハードコード一覧で
持っていた。 **新しい `.py` を足して追記を忘れると、実機だけで
`ModuleNotFoundError` になる**（`MAYA_HOT_UPDATE_PATTERNS.md` §1-10 で実際に
踏んだ事故）。 これは自宅では**絶対に再現しない** — ローカルにはファイルが
存在するので、テストも import も普通に通ってしまう。

**ハブ化でこの宣言ごと廃止した。** ハブは tree walk でパッケージの中身を全部
配るので、「足したのに配られない」が原理的に起きない。

ただし**別の穴が 1 つ残る**: ハブは配布対象を拡張子で絞っている
（`_ALLOWED_SUFFIXES`）。 未登録の拡張子でリソースを足すと、やはり実機にだけ
届かない。 そこで `tests/test_installer.py` が **パッケージ内の全ファイルが
配布対象に入っているか**を実リポジトリに対して突き合わせる。 §1-10 の検査を
この 1 つに置き換えた形。

同じ理由で、`tests/test_installer.py` は「`check_tools.py` が見るツールを
ハブも漏れなく拾えるか」も検査する。 **どちらか一方の定義がずれると、
検査は通るのに実機には何も届かない**という最悪の形になるため。

## テストが担保するもの・しないもの

**担保する**
- メタ情報と配布設定の整合性（バージョン 3 箇所同期、`_REMOTE_FILES`、GitHub 座標）
- 命名規約（ウィンドウ名 `<モジュール名>Win`）
- Maya の Python バージョンで解析できる構文か
- `core.py` の純ロジック — **関数の入出力・境界条件。 実機と同じ結果が出る唯一の層**
- `show()` の一往復（ウィンドウ生成 / 二重生成しない / undo チャンクの閉じ忘れ）

**担保しない**
- 実 Maya でのノード操作・UI の見た目・`cmds` の実挙動

`tests/_bootstrap.py` の `maya.cmds` スタブは「呼ばれたこと」しか知らない。
**テストが全部通っても、実機で動く保証にはならない。** ここで担保しているのは
「壊れた状態で実機に持っていかない」ことだけで、機能の正しさは実機確認が要る。

だから報告と `docs/PROGRESS.md` には、必ず**どの版がどこまで実機確認済みか**を
書く。 「実装済み・実機未確認」が溜まるのがこのワークスペースの常態なので、
それを追える形にしておかないと「動いているつもり」で次を積み上げることになる。

## 雛形の実体

`docs/templates/tool_template/` にある。 置換すべき語は 3 つ:

| 置換前 | 置換後 | 使われている場所 |
|---|---|---|
| `tool_template` | `<tool_name>` | フォルダ名・モジュール名・ウィンドウ名・optionVar キー |
| `Tool Template` | `<表示名>` | ウィンドウタイトル・ドキュメント |
| `ToolTmpl` | `<シェルフラベル>` | シェルフボタン |

**置換のほかに手で決めるものは無い。** `ui.py` の `WINDOW` も optionVar キーも
`NAMESPACE` と `__package__` から組み立ててあるので、フォルダ名を変えれば自動で
追従する。

### 名前空間の扱い（間違えやすい）

`ntk` を **ツール名には付けず、実行時識別子には必ず付ける**（CLAUDE.md「ルール」）。
同じ札でも役割が正反対なので、雛形では層を分けてある。

| | 例 | 誰が読むか |
|---|---|---|
| ツール名 | `rename_helper` / `Rename Helper` / `RenameHlp` | **人**（社内で配る相手） |
| 実行時識別子 | `ntk_rename_helperWin` / `ntk_rename_helper_last_target` | **Maya**（フラットな名前空間） |

配る相手にとって個人名の接頭辞は意味を持たないので、前者からは外す。 後者は
Maya が 1 つの空間を共有していて、`lastTarget` のような汎用名は他人のツールと
**後勝ちで静かに衝突する**ため、社内配布ではむしろ必須になる。

変えるときに触るのは `NAMESPACE`（`__init__.py`）と `_NAMESPACE`（`install.py`）の
2 箇所だけ。 ずれると更新時に古いウィンドウを閉じ損なうので、
`check_tools.py` とテストが突き合わせる。

雛形はコピーした時点で 17 件のテストが通り、`check_tools.py` が `0 error` になる
（ルート README への行追加を除く）。 通らなくなったら置換漏れを疑う。
