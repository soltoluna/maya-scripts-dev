# Color Override — 変更履歴

現時点の仕様と確定した設計判断は `SPEC.md` を参照。 ここではバージョンごとの
経緯・試行錯誤・不具合修正の細部を記録する。 降順（新しい順）。

## 0.4.0 — セット・色見本・控えからの呼び戻し

実機からの要望 3 つ。 どれも「まとめて掛けたあとの扱い」に効く。

1. **Restore All した後でも任意のタイミングで元に戻したい**
2. **まとめて掛けても一覧がオブジェクトごとにならないようにしたい。 命名して
   一括管理できるとよい**
3. **一覧にカラーコードではなく色を表示したい**（コードを見ても色が分からない）

2 と 3 は素直に「1 回の Apply = 1 セット」と `cmds.canvas` の色見本で入る。
1 が設計判断を要した。

### 控えをどこに置くか

素直にやるならセットをシーンのノードに持たせて `Restore` でも消さない形に
なるが、**利用者から「Restore All で Maya データはきれいな状態にしたい」**と
指摘があった。 ツール由来のノードがシーンに残るのはリスクだという判断で、
これは正しい。

そこで **シーンには一切残さず、シーンファイルの隣に JSON を置く**形にした。

    <シーン名>.color_override.json

- 掛かっている間のセット名はシェーダーの属性（`Restore` で一緒に消える）
- 片付けたあとの色分けは JSON（シーンとは独立に残る）

**控えは「読み込む」操作を作らず、一覧に混ぜて出す。** 片付けたセットが
`控え` の行として並び続け、`Apply` で戻る。 別の操作にすると、片付けた
ものを見失って「戻せることを知らないまま掛け直す」ことになる。

### 決めたこと

- **戻し先（元の shadingEngine）は控えに書かない。** 呼び戻すのは別の
  セッション・別のシーン状態かもしれないので、そのときの割り当てを見て
  取り直す。 古い戻し先を持ち回ると、もう存在しない SG へ戻そうとして事故る
- **控えが書けなかったら片付けそのものを中止する**（`_backup_sets` が
  `False` を返す）。 消してから「書けませんでした」では遅い
- **シーンが未保存なら 3 択で尋ねる**（保存先を選ぶ / 控えずに片付ける /
  キャンセル）。 黙って控えずに消すと、戻せないことに後から気づく
- **JSON は人が読める形で書き、読むときは全面的に疑う。** 手で開いて直せる
  ほうが、こちらが読めないより良い。 1 項目が壊れていても残りは使う
- **色見本は同じ色を 1 つに畳む。** 12 個に 1 色を掛けたセットは見本 1 個で
  足りる。 ばらばらに振ったセットだけが複数個になり、8 個を超えたら `+N`
- 一覧は `textScrollList` では色を出せないので、`scrollLayout` の中に
  `rowLayout` を並べて毎回作り直す形にした

### 後始末

`core.format_row`（`名前   #RRGGBB` の 1 行を作る関数）は、色見本表示に
変えたことで使い道が無くなったので消した。

## 0.3.0 — グループノードに掛けると元に戻らない不具合を修正

実機からの報告: **黒髪のグループノードに色を掛けて Restore したらグレーに
なった。**

原因は `_shapes_of()` のシェイプ解決。 `listRelatives(shapes=True)` は
**グループの直下にシェイプが無い**（子はトランスフォーム）ので空を返し、
v0.2.0 まではそこでノード自身にフォールバックしていた。 結果、グループ
トランスフォームに対して `listConnections(type="shadingEngine")` を引いて
何も見つからず、**戻し先を `initialShadingGroup`（＝グレーの lambert1）として
記録**していた。 色が正しく乗っていたのは `cmds.sets` がグループ配下の
シェイプへ伝播するためで、掛ける側だけが偶然動いていた。

自宅では Maya が無く、スタブは `listRelatives` の戻り値を模擬しないので
**このクラスの不具合はテストでは絶対に出ない**。

修正は 2 段:

1. **シェイプ解決を `ls(dag=True, shapes=True)` に変えた。** 部分木を
   たどるので、グループでも中のシェイプを全部拾う
2. **戻し先をメンバーごとに持つようにした**（`.ntkColorOverrideOriginals`）。
   グループの中身は別々のマテリアルを持ちうるので、1 件に 1 つでは
   そもそも戻せない。 `core.align_originals` がメンバーと戻し先を 1 対 1 に
   揃え、長さが食い違ったら旧形式の単一値で埋める（v0.2.0 までのシーンを
   開いても壊れないため）

派生して決めたこと:

- **1 シェイプ = 1 オーバーライド を保つ**（`_release_members`）。 グループに
  掛けたあと中の 1 つだけ色を変えると、そのシェイプは新しい記録へ移り、
  古い記録から外れる。 メンバーが 0 になった記録はシェーダーごと片付ける。
  これをしないと同じシェイプが 2 つの記録に属し、どちらの Restore が
  勝つかで結果が変わる
- **割り当てはグループではなく解決したシェイプに対して行う。**
  `cmds.sets` の伝播に頼ると、記録した相手と実際に色が乗った相手がずれる
- `Restore Selected` は選択をシェイプまで広げてから突き合わせる。
  記録が抱えているのはシェイプなので、グループや子を選んだままでは
  一致しなかった

**既に v0.2.0 以前で掛けたシーンは救えない。** 戻し先の情報がどこにも
記録されていないため。 該当するシーンは Restore せずに開き直すしかない。

## 0.2.0 — 一時解除（peek）を追加

「一時的に元のマテリアルに戻したい」という要望から。 色を振り直さずに
元の見た目と往復できるようにした。

`Restore` を流用せず別操作にしたのは、**シェーダーとセットを消してしまうと
戻したときに色が変わる**ため。 `distinct_colors` は掛かっている数を開始
インデックスにするので、一度片付けてから掛け直すと同じ色にならない。
確認のための往復で色が変わるのでは用を成さない。

実装で効いた判断:

- **解除中かどうかのフラグを持たない。** shadingEngine にメンバーが居るかが
  そのまま状態。 フラグを別に持つと、Maya 側で手作業に割り当てを変えられた
  ときに表示と食い違う（このツールが一貫して「シーンの実態が情報源」で
  作られているのと同じ理由）
- **掛けた相手を `.ntkColorOverrideMembers` に控える。** 外した瞬間に
  shadingEngine が空になり、「何に掛かっていたか」がシーンから読めなくなる。
  シーンに書くので、解除したまま保存して開き直しても戻せる
- **既存オーバーライドの照会を、シーンの割り当てから記録の索引に変えた。**
  v0.1.0 は対象の現在の shadingEngine を辿って既存を探していたが、
  **解除中は対象が元の SG に戻っているので見つけられない**。 見つけ損なうと
  2 本目のシェーダーを作り、元のマテリアルの記録が二重になる。 索引
  （`core.index_by_object`）は 1 回のスキャンで作るので、対象ごとに
  `listConnections` を辿るより速くもなった
- **戻し先が同じものは 1 回の `cmds.sets` にまとめる**（`core.group_by_original`）。
  一時解除は全件を一度に動かす操作なので、対象ごとに呼ぶと数百オブジェクトで
  往復が効いてくる
- `toggle()` をパッケージ直下に公開した。 ウィンドウを開いていなくても動くので
  ホットキーに割り当てられる。 「一瞬だけ見たい」のが用途なので、ボタンまで
  マウスを運ばずに往復できるほうが速い

## 0.1.0 — 初版

同じような色のオブジェクトの貫通をビューポートで見分けたい、という要望から。

**当初案（Render Setup でオブジェクト ID をオーバーライド）は採らなかった。**
理由は 2 つ:

1. Render Setup のシェーダーオーバーライドは **collection 単位**なので、
   オブジェクトごとに色を変えるには対象の数だけ collection を作ることになる
2. 1 枚のシェーダーで対象ごとに色を変えられる Arnold の `aiUtility`
   （Color Mode: Object）は、**ビューポートに反映されない**（ARV / レンダリングのみ）。
   目的が目視確認なので致命的

確認用の一時的な塗り分けにルック開発のレイヤー構造を使うことにもなるため、
**シェーダー割り当てを直接触って、元に戻せるようにする**方針にした。

実装上の判断:

- **復元情報はシーンに書く**（オーバーライド用シェーダーの文字列属性）。
  Python 側の辞書に持つと、シーンを保存して開き直した時点で戻せなくなる
- **管理対象の判別は名前ではなく属性の有無で行う。** 名前で判別すると、
  ユーザーがノードをリネームした瞬間に孤児になる
- **掛け直しでは既存のオーバーライドを先に探す。** 探さずに現在の
  shadingEngine を「元の SG」として記録すると、オーバーライド用の SG を
  記録してしまい**二度と元のマテリアルに戻せなくなる**。 実装中に一番
  危ないと判断した箇所で、`_existing_override()` として切り出してある
- **色は乱数ではなく色相を黄金比でずらして生成する。** 等間隔だと周期で色が
  戻り、乱数だと掛け直すたびに色が入れ替わって「さっきと同じものを見ている」
  確信が持てなくなる
