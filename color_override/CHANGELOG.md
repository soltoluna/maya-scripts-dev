# Color Override — 変更履歴

現時点の仕様と確定した設計判断は `SPEC.md` を参照。 ここではバージョンごとの
経緯・試行錯誤・不具合修正の細部を記録する。 降順（新しい順）。

## 0.9.0 — Hide でフェース割り当てが消えるのを修正

v0.8.0 で色は乗るようになったが、**Hide すると単一マテリアルになり、
ファセットアサインが消える**（実機からの指摘）。 戻す側ではなく、
**掛けるときに分割を拾えていなかった**。

### 読み取る経路を変えた

v0.5.0 から `instObjGroups[0].objectGroups[n].objectGrpCompList` を直接
読んでいた。 接続をたどるだけで済み、SG のメンバーを引かずに安く上がる —
という理屈だったが、**実機では塊が 1 つも取れていなかった**。
（v0.7.1 で「空 = オブジェクト全体のメンバー」と解釈を直したので、
フェース割り当ても「全体」として素通りしていた。 v0.8.0 で色は乗るように
なったが、控えは空のまま。）

`cmds.sets(sg, q=True)` に寄せた。 **割り当てを読むのに広く使われている
経路**で、コンポーネントは `pCubeShape1.f[0:2]` の形で返る。

**安さより、読めることを優先した。** 3 回続けて読み取りの想像で外している。

### 安さは別の形で確保した

`cmds.sets(sg, q=True)` は `initialShadingGroup` で数千件返りうる。
そのままでは掛けるたびに走査することになるので、

- **つながっている shadingEngine が 1 つならそこで打ち切る。** フェースで
  分かれていても行き先が 1 つなら、シェイプ全体で戻して同じ結果になる。
  ふつうのシェイプはここで終わるので、**セットの中身を引かない**
- 2 つ以上のときだけメンバーを引き、**SG ごとに 1 回だけ**引いて使い回す
  （`_sg_member_reader`）

### 持ち主はフルパスで突き合わせる

SG のメンバーには他のシェイプのコンポーネントも混ざっている。 短い名前で
照合すると、`|charA|body|bodyShape` と `|charB|body|bodyShape` のような
同名シェイプのフェースを取り込み、**他人のフェースを別のマテリアルへ戻す**
事故になる。 フルパスでのみ一致とみなす。

### 拾えなかったら掛けるときに言う

shadingEngine が 2 つ以上つながっているのにコンポーネントを 1 つも拾えない
なら、それは想定外。 **その場で警告する**（Hide してから気付くのでは遅い）。
色は掛ける（v0.8.0 の方針は維持）。

## 0.8.0 — 主機能を止めうる経路を無くし、調べる手段を足す

v0.7.1 でも実機では色が乗らなかった。 **読み取りの当て推量を重ねるのをやめる。**

### 判断を撤回した

v0.5.0 で入れた「フェース割り当てを読めないなら掛けない」は、意図としては
正しかった（掛けた時点で元の分割が落ちるので、読めないまま進むと戻せない）。
だが実機では**その判断が働いて色がまったく乗らなくなった**。 v0.7.1 で
原因と踏んだ `objectGroups` の空の扱いを直しても、まだ乗らない。

ここで方針を変えた。 **色を塗ることがこのツールの主機能で、フェース分割の
復元は付随的。 付随的なもののために主機能が止まる作りそのものが間違い。**

- 読み取れなくても**掛ける**。 警告だけ出して、そのシェイプは v0.4.0 と
  同じ「シェイプ全体を 1 つの SG へ戻す」に落ちる
- `_read_assignment` は**例外を上げない**（詳しい読み取り → 簡易読み取り →
  `initialShadingGroup` の順に落ちる）。 途中で落ちると `_apply_one` ごと
  止まり、やはり色が乗らない

これで、フェース読み取りが実機で何を返そうと **Apply は最低でも v0.4.0 と
同じように動く**。

### 調べる手段を足した

`color_override.diagnose()` を追加。 選択物について

- `listConnections(type="shadingEngine")`（簡易）
- `listConnections(..., connections=True, plugs=True)`（詳しい読み取り）
- 各 `objectGroups[n].objectGrpCompList`
- `_read_assignment()` の結果

を生の repr で出す。 途中で例外が出ても `<ERROR ...>` と値にして続ける。

**開発機に Maya が無い以上、実機の戻り値は持ち帰るしかない。** 3 回外した
あとで言うのも遅いが、最初にこれを入れておくべきだった。

### 控えの選択がシーンをまたいでいた

「新規シーンでも前に開いていた控えが読み込まれている」— そのとおりで、
optionVar は Maya の設定として残るので、シーンを変えても選択が生き続けていた。

- 選んだときの**シーン名も一緒に覚え**、食い違えば捨てる
- **未保存 → 新規シーン**はどちらもシーン名が空なので見分けられない。
  `NewSceneOpened` / `SceneOpened` の scriptJob で捨てる。 ジョブは
  ウィンドウに紐付けてあるので、閉じれば一緒に消える（外し忘れが起きない）

## 0.7.1 — Apply しても色が変わらない を修正

実機からの報告。 **v0.5.0 で入れた「フェース割り当てを読めないなら掛けない」
判定が、ふつうのシェイプにまで働いていた。**

### 取り違えていたこと

`instObjGroups[0].objectGroups[n]` を**フェース単位の割り当ての印**として
扱っていた。 実際には `objectGroups` は**オブジェクト全体のメンバーシップでも
経由する**。 そのとき `objectGrpCompList` は空になる。

v0.5.0 の `_component_list()` は「空 = 読めなかった」と返していたので、

  `objectGroups` を経由しているふつうのシェイプ
   → 塊が読めない
   → 「掛けると戻せなくなる」と判断
   → **そのノードごと飛ばす**
   → **色がまったく掛からない**

安全弁（A）がツールの主機能を止めていた。 いちばん避けたかった形の事故で、
しかも**自宅では絶対に再現しない**（スタブは割り当てを持たないので、
`objectGroups` がどう返るかを試せない）。

### 直したこと

`_component_list()` を `(塊, 読めたか)` の 2 値にした:

| `objectGrpCompList` | 判断 |
|---|---|
| 中身がある | フェース単位の塊 |
| **空 / None** | **オブジェクト全体のメンバー**（`wholes` へ） |
| `getAttr` が失敗 | 読めなかった → 掛けない |
| 中身があるのに `f[...]` が取れない | 読めなかった → 掛けない |

### もう一段の逃げ道

`listConnections(connections=True, plugs=True)` 自体が通らない環境に当たった
場合も、**v0.4.0 の簡易読み取り（`_simple_engine_of`）に落として色は掛ける**。

**色を塗るのがこのツールの主目的で、それが丸ごと動かなくなるほうが害が大きい。**
フェース分割の復元は「できれば守る」であって、主機能を止めてまで守るもの
ではなかった。 v0.5.0 はそこの優先順位を間違えていた。

### 切り分けやすくした

掛からなかったオブジェクトは**名前まで**完了ログに出す:

```
[color_override] apply color: 0 object(s) -> Set 1  skipped: 2 (body_geo, hair_geo)
```

件数だけだと、どれが掛からなかったのかを探すところから始めることになる。

## 0.7.0 — 読み込む控えを選べるようにする

実機からの指摘 3 つ。 **うち 2 つ（復元ボタンが無い・ファセットが消える）は
v0.5.0 / v0.6.0 で直した分で、まだ push していなかったため実機に届いて
いなかった。** ここで直したのは 3 つ目。

### 読み込む控えを選びたい

控えの置き場所はシーンの隣に固定していた。 決め打ちで済むと思っていたが、
実機では届かない場面がある:

- **シーンが未保存**で、控えを自分で選んだ場所に置いた
- **別名保存で置いてきた前のシーンの控え**を呼び戻したい
- **共有フォルダに置いた色分け**を他の人と使い回したい

控え欄に `読み込む…` と `既定` を足し、選んだ控えを既定より優先するように
した。 v0.6.0 は optionVar を**未保存シーンのときしか見ていなかった**ので、
選んでも既定に戻ってしまう作りだった（`_backup_path()` の分岐を
「選択 → 既定」の順に入れ替えた）。

**読めなかった控えには切り替えない。** 空や壊れた JSON に切り替えてしまうと、
それまで見えていた控えまで見失う。

### 空でも欄を畳まない — v0.6.0 の判断を戻した

v0.6.0 では「控えが 0 件なら欄ごと `manage=False`」にしていた。 空の箱に縦を
取らせない意図だったが、**「控えたのに 0 件」のときにこそ選び直したい**のに、
その入口ごと消えることになる。 今回の指摘（未保存シーンで控えたのに
`0 backup`）はまさにその状態なので、常設に戻した。

あわせて欄の左上に**いま見ている控えのファイル名**を出す。 `0 セット` だけでは
「未保存なのか / 空なのか / 別の控えを見ているのか」が切り分けられない。

### 実機確認（未実施）

SPEC.md の「実装状況 v0.7.0」に手順を残した。 `fileDialog2` は自宅では
動かないので、**控えを選ぶ往復は一度も通していない。**

## 0.6.0 — 控えを別の欄に分け、「復元」を置く

実機からの指摘 —「控えを書き出すだけで、復元ボタンがない。 Restore しても
一覧に残ってしまう」。

### 見え方の問題

v0.4.0 の一覧は、掛かっているセットと控えのセットを**同じ欄に混ぜて**いた。
控えの行には `Apply` ボタンを置いてあったが、

- `Restore` を押してもその場に行が残るので、**片付いたのかどうか分からない**
- `Apply` は上の「Apply to Selected」と同じ語なので、**「いま選んでいる色を
  掛ける」**と読める。 復元の手段だと気付けない

機能はあったのに、**無いのと同じ**だった。

### 分けた

上の一覧は掛かっているセットだけ。 控えは下の `frameLayout` に移し、ボタンは
`復元` にした。 `Restore` すると上から消えて下に現れ、`復元` を押すと上に戻る。
**操作と見え方が 1 対 1 になる。**

控えが 0 件のうちは欄ごと `manage=False` で畳む。 空の箱に縦を取らせない
（2 欄になったぶんウィンドウは 510 → 560px に伸ばした）。

### ついでに見つけた穴 — 控えの置き場所を覚えていなかった

`_ask_backup_path()` は**未保存シーンのときだけ**保存先を尋ねるが、選ばれた
パスをどこにも覚えていなかった。 一方 `_read_backup()` は `_backup_path()`
＝**シーンの隣**しか見ない。

つまり**未保存シーンで控えを書き出すと、そのファイルは二度と読まれない。**
一覧にも出ないので、復元の手段が本当に無くなる。 指摘の「復元ボタンがない」は
この状態を踏んでいた可能性がある。

optionVar `ntk_color_override_backup_path` に覚えて、シーンが未保存なら
そこを見るようにした。

### 実機確認（未実施）

SPEC.md の「実装状況 v0.6.0」に手順を残した。 特に **未保存シーンでの
往復**（Restore → 保存先を選ぶ → 控え欄に出る → 復元）は自宅では
`fileDialog2` が動かないので一度も通していない。

## 0.5.0 — フェース単位の割り当てを壊さない

「ファセットが使われているモデルでも問題なく動くか（Restore も含めて）」という
確認から。 **答えは「動くが、静かに壊していた」。**

### 何が起きていたか

フェースごとに別マテリアルが割り当たったメッシュに色を掛けると:

1. 控えるのは `listConnections(shape, type="shadingEngine")` の**先頭 1 つだけ**
2. `cmds.sets(shape, forceElement=...)` が**シェイプ全体**を掛けるので、
   その場で元のフェース割り当てが外れる
3. Restore では控えた 1 つの SG へシェイプ全体を戻す
   → **3 マテリアルのメッシュが 1 色のマテリアルに潰れる**

しかも `Hide`（一時解除）でも同じ経路を通るので、「ちょっと外して見る」だけで
失われていた。 控えの JSON も戻し先を持たない設計なので、そこからも救えない。
回復手段は undo だけ、保存して開き直したら終わり。

### 2 つ入れた

**掛けない（安全弁）** — 塊を読み取れないシェイプには色を掛けず、警告して
飛ばす。 掛けた時点で元の分割が落ちるので、**読めないなら触らない**のが唯一
安全な振る舞いになる。 グループを渡したときは中の 1 つでも読めなければ
そのノードごと飛ばす（半分だけ掛かっているほうが分かりにくい）。

**控えて戻す（本対応）** — 掛ける前に「どの SG にどのフェースが入っていたか」を
シェーダーの `.ntkColorOverrideFaces`（JSON）に控え、Restore と Hide で
分割ごと戻す。

### 読み取りをどこから取るか

`cmds.sets(sg, q=True)` で SG 側からメンバーを引くのが素直だが、**これは
`initialShadingGroup` を舐めることになる**。 大きいシーンでは数千件が返り、
オブジェクトごとに引けば掛けるたびに効いてくる。

採ったのは接続をたどる方法。 フェース割り当ては
`shape.instObjGroups[0].objectGroups[n]` → `SG.dagSetMembers[i]` の形でつながるので、

- `listConnections(shape, type="shadingEngine", connections=True, plugs=True)` の
  **プラグの形**（`.objectGroups[` を含むか）でフェース割り当てかどうかが分かる
- 塊そのものは `objectGroups[n].objectGrpCompList` から直接取れる

ふつうのシェイプ（＝ほとんど全部）は 1 本目の `listConnections` だけで判定が
終わり、追加の `getAttr` を踏まない。 元の実装と同じ往復回数で済む。

### 戻す順序でもう一度ひっかかった

塊だけ戻すと、**どの塊にも入っていないフェース**がオーバーライド用の SG に
残る。 Restore はそのあと SG ごと削除するので、そこだけ割り当てを失う。

なので `core.restore_plan` は 2 段階を返す — 先にシェイプ全体を土台の SG へ
戻し、そのあと塊を割り当て直す。 土台はシェイプ全体に掛かっていた SG、
それが無ければ最初の塊の SG。 これで取りこぼしが出ない。

`core.group_by_original` は `restore_plan` に置き換えた（戻し先の組み立てが
2 本あると、片方だけフェースを知っている状態になって必ず食い違う）。

### 残っている制約

- 掛けるときは従来どおり**シェイプ全体が 1 色**。 フェースを選んで色を
  分けることはできない（貫通の判別が目的なので、そこまでは要らないと判断）
- 元が**割り当て無し**だったフェースは、戻すと土台の SG に入る
- **v0.4.0 以前に掛けたままのシーン**には控えが無いので、従来どおり 1 つに寄る

### 実機確認（未実施）

開発機に Maya が無いので、**フェース分けされたモデルで戻ることは一度も
確かめていない**。 SPEC.md の「実装状況 v0.5.0」に手順を残した。

## 0.4.0 — セット・色見本・控えからの呼び戻し

実機からの要望 3 つ。 どれも「まとめて掛けたあとの扱い」に効く。

1. **Restore All した後でも任意のタイミングで元に戻したい**
2. **まとめて掛けても一覧がオブジェクトごとにならないようにしたい。 命名して
   一括管理できるとよい**
3. **一覧にカラーコードではなく色を表示したい**（コードを見ても色が分からない）

2 と 3 は素直に「1 回の Apply = 1 セット」と `cmds.canvas` の色見本で入る。
1 が設計判断を要した。

### 控えをどこに置くか

素直にやるならセットをシーンのノードに持たせて `Restore` でも消さない形に
なるが、**利用者から「Restore All で Maya データはきれいな状態にしたい」**と
指摘があった。 ツール由来のノードがシーンに残るのはリスクだという判断で、
これは正しい。

そこで **シーンには一切残さず、シーンファイルの隣に JSON を置く**形にした。

    <シーン名>.color_override.json

- 掛かっている間のセット名はシェーダーの属性（`Restore` で一緒に消える）
- 片付けたあとの色分けは JSON（シーンとは独立に残る）

**控えは「読み込む」操作を作らず、一覧に混ぜて出す。** 片付けたセットが
`控え` の行として並び続け、`Apply` で戻る。 別の操作にすると、片付けた
ものを見失って「戻せることを知らないまま掛け直す」ことになる。

### 決めたこと

- **戻し先（元の shadingEngine）は控えに書かない。** 呼び戻すのは別の
  セッション・別のシーン状態かもしれないので、そのときの割り当てを見て
  取り直す。 古い戻し先を持ち回ると、もう存在しない SG へ戻そうとして事故る
- **控えが書けなかったら片付けそのものを中止する**（`_backup_sets` が
  `False` を返す）。 消してから「書けませんでした」では遅い
- **シーンが未保存なら 3 択で尋ねる**（保存先を選ぶ / 控えずに片付ける /
  キャンセル）。 黙って控えずに消すと、戻せないことに後から気づく
- **JSON は人が読める形で書き、読むときは全面的に疑う。** 手で開いて直せる
  ほうが、こちらが読めないより良い。 1 項目が壊れていても残りは使う
- **色見本は同じ色を 1 つに畳む。** 12 個に 1 色を掛けたセットは見本 1 個で
  足りる。 ばらばらに振ったセットだけが複数個になり、8 個を超えたら `+N`
- 一覧は `textScrollList` では色を出せないので、`scrollLayout` の中に
  `rowLayout` を並べて毎回作り直す形にした

### 後始末

`core.format_row`（`名前   #RRGGBB` の 1 行を作る関数）は、色見本表示に
変えたことで使い道が無くなったので消した。

## 0.3.0 — グループノードに掛けると元に戻らない不具合を修正

実機からの報告: **黒髪のグループノードに色を掛けて Restore したらグレーに
なった。**

原因は `_shapes_of()` のシェイプ解決。 `listRelatives(shapes=True)` は
**グループの直下にシェイプが無い**（子はトランスフォーム）ので空を返し、
v0.2.0 まではそこでノード自身にフォールバックしていた。 結果、グループ
トランスフォームに対して `listConnections(type="shadingEngine")` を引いて
何も見つからず、**戻し先を `initialShadingGroup`（＝グレーの lambert1）として
記録**していた。 色が正しく乗っていたのは `cmds.sets` がグループ配下の
シェイプへ伝播するためで、掛ける側だけが偶然動いていた。

自宅では Maya が無く、スタブは `listRelatives` の戻り値を模擬しないので
**このクラスの不具合はテストでは絶対に出ない**。

修正は 2 段:

1. **シェイプ解決を `ls(dag=True, shapes=True)` に変えた。** 部分木を
   たどるので、グループでも中のシェイプを全部拾う
2. **戻し先をメンバーごとに持つようにした**（`.ntkColorOverrideOriginals`）。
   グループの中身は別々のマテリアルを持ちうるので、1 件に 1 つでは
   そもそも戻せない。 `core.align_originals` がメンバーと戻し先を 1 対 1 に
   揃え、長さが食い違ったら旧形式の単一値で埋める（v0.2.0 までのシーンを
   開いても壊れないため）

派生して決めたこと:

- **1 シェイプ = 1 オーバーライド を保つ**（`_release_members`）。 グループに
  掛けたあと中の 1 つだけ色を変えると、そのシェイプは新しい記録へ移り、
  古い記録から外れる。 メンバーが 0 になった記録はシェーダーごと片付ける。
  これをしないと同じシェイプが 2 つの記録に属し、どちらの Restore が
  勝つかで結果が変わる
- **割り当てはグループではなく解決したシェイプに対して行う。**
  `cmds.sets` の伝播に頼ると、記録した相手と実際に色が乗った相手がずれる
- `Restore Selected` は選択をシェイプまで広げてから突き合わせる。
  記録が抱えているのはシェイプなので、グループや子を選んだままでは
  一致しなかった

**既に v0.2.0 以前で掛けたシーンは救えない。** 戻し先の情報がどこにも
記録されていないため。 該当するシーンは Restore せずに開き直すしかない。

## 0.2.0 — 一時解除（peek）を追加

「一時的に元のマテリアルに戻したい」という要望から。 色を振り直さずに
元の見た目と往復できるようにした。

`Restore` を流用せず別操作にしたのは、**シェーダーとセットを消してしまうと
戻したときに色が変わる**ため。 `distinct_colors` は掛かっている数を開始
インデックスにするので、一度片付けてから掛け直すと同じ色にならない。
確認のための往復で色が変わるのでは用を成さない。

実装で効いた判断:

- **解除中かどうかのフラグを持たない。** shadingEngine にメンバーが居るかが
  そのまま状態。 フラグを別に持つと、Maya 側で手作業に割り当てを変えられた
  ときに表示と食い違う（このツールが一貫して「シーンの実態が情報源」で
  作られているのと同じ理由）
- **掛けた相手を `.ntkColorOverrideMembers` に控える。** 外した瞬間に
  shadingEngine が空になり、「何に掛かっていたか」がシーンから読めなくなる。
  シーンに書くので、解除したまま保存して開き直しても戻せる
- **既存オーバーライドの照会を、シーンの割り当てから記録の索引に変えた。**
  v0.1.0 は対象の現在の shadingEngine を辿って既存を探していたが、
  **解除中は対象が元の SG に戻っているので見つけられない**。 見つけ損なうと
  2 本目のシェーダーを作り、元のマテリアルの記録が二重になる。 索引
  （`core.index_by_object`）は 1 回のスキャンで作るので、対象ごとに
  `listConnections` を辿るより速くもなった
- **戻し先が同じものは 1 回の `cmds.sets` にまとめる**（`core.group_by_original`）。
  一時解除は全件を一度に動かす操作なので、対象ごとに呼ぶと数百オブジェクトで
  往復が効いてくる
- `toggle()` をパッケージ直下に公開した。 ウィンドウを開いていなくても動くので
  ホットキーに割り当てられる。 「一瞬だけ見たい」のが用途なので、ボタンまで
  マウスを運ばずに往復できるほうが速い

## 0.1.0 — 初版

同じような色のオブジェクトの貫通をビューポートで見分けたい、という要望から。

**当初案（Render Setup でオブジェクト ID をオーバーライド）は採らなかった。**
理由は 2 つ:

1. Render Setup のシェーダーオーバーライドは **collection 単位**なので、
   オブジェクトごとに色を変えるには対象の数だけ collection を作ることになる
2. 1 枚のシェーダーで対象ごとに色を変えられる Arnold の `aiUtility`
   （Color Mode: Object）は、**ビューポートに反映されない**（ARV / レンダリングのみ）。
   目的が目視確認なので致命的

確認用の一時的な塗り分けにルック開発のレイヤー構造を使うことにもなるため、
**シェーダー割り当てを直接触って、元に戻せるようにする**方針にした。

実装上の判断:

- **復元情報はシーンに書く**（オーバーライド用シェーダーの文字列属性）。
  Python 側の辞書に持つと、シーンを保存して開き直した時点で戻せなくなる
- **管理対象の判別は名前ではなく属性の有無で行う。** 名前で判別すると、
  ユーザーがノードをリネームした瞬間に孤児になる
- **掛け直しでは既存のオーバーライドを先に探す。** 探さずに現在の
  shadingEngine を「元の SG」として記録すると、オーバーライド用の SG を
  記録してしまい**二度と元のマテリアルに戻せなくなる**。 実装中に一番
  危ないと判断した箇所で、`_existing_override()` として切り出してある
- **色は乱数ではなく色相を黄金比でずらして生成する。** 等間隔だと周期で色が
  戻り、乱数だと掛け直すたびに色が入れ替わって「さっきと同じものを見ている」
  確信が持てなくなる
